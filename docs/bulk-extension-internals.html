TSD.BulkExtensions · tài liệu nội bộ

Giải phẫu Bulk Extension

Bên trong EFCore.BulkExtensions làm gì khi gọi BulkInsertAsync: từ metadata của EF Core, qua SqlBulkCopy hoặc COPY BINARY, tới câu MERGE và cách lấy lại Id. Đây là cơ chế mà TSD.BulkExtensions sẽ tái tạo.

Nguồn: fork MIT tại commit 5bf938a4 (01/2023) + bản 6.5.6 TruePos đang dùng Cập nhật: 2026-09-11

1. Vì sao cần bulk

SaveChanges của EF Core gửi mỗi entity thành một câu INSERT/UPDATE riêng (EF 6 gộp tối đa 42 câu một batch, nhưng vẫn là từng câu). Với 100.000 dòng, đó là hàng nghìn round-trip và server phải parse hàng nghìn statement. Bulk extension đi đường khác: đẩy toàn bộ dữ liệu xuống server bằng giao thức stream chuyên dụng, rồi chạy một câu SQL tập hợp.

Thao tácEF Core SaveChangesBulk extension
Insert 100K dòng~2.400 batch INSERT, change tracker giữ 100K entry1 phiên SqlBulkCopy / COPY, không change tracker
Update 100K dòngPhải load trước hoặc Attach từng entity, rồi UPDATE từng dòngStream vào bảng tạm, 1 câu MERGE / UPDATE FROM
UpsertKhông có API, phải tự query rồi rẽ nhánhMERGE WHEN MATCHED / NOT MATCHED, hoặc ON CONFLICT
Lấy Id sinh raTự động, vì từng câu INSERT trả vềPhải thiết kế riêng: OUTPUT / RETURNING + ánh xạ ngược

Cột cuối là phần khó nhất. Stream dữ liệu thì nhanh, nhưng server không biết dòng nào của mình là entity nào trong bộ nhớ. Phần lớn độ phức tạp của thư viện nằm ở việc giải bài toán ánh xạ ngược này.

2. Kiến trúc 4 tầng

Thư viện có ~9.200 dòng nhưng chia rất rõ thành bốn tầng. Consumer chỉ chạm tầng 1. TSD.BulkExtensions giữ nguyên cấu trúc này.

Tầng 2 và 3 là phần “trung tính”, chiếm khoảng 45% code. Tầng 4 mỗi provider ~1.000 dòng cho SQL Server và ~450 dòng cho PostgreSQL. Đây là cơ sở để ước lượng: viết lại lõi + 2 provider tương đương khoảng 4.500 dòng code sản phẩm sau khi cắt tính năng không dùng.

3. Luồng điều phối

Mọi lời gọi công khai đều đổ về một hàm: DbContextBulkTransaction.Execute(context, type, entities, operationType, bulkConfig, progress). Hàm này quyết định đi nhánh nào.

Trước khi rẽ nhánh, TableInfo.CreateInstance chạy để đọc model. Riêng nhánh Delete chỉ nạp cột khoá (loadOnlyPKColumn) vì MERGE … DELETE không cần cột khác.

4. TableInfo: đọc model EF thành bản đồ cột

Đây là file lớn nhất (1.375 dòng) và là nơi chứa 6 năm sửa lỗi. Nó không sinh SQL, chỉ trả lời câu hỏi: với entity type này và config này, cột nào đi vào bảng tạm, cột nào so sánh, cột nào update, cột nào server tự sinh?

Ba dict cột là chìa khoá hiểu MERGE: PropertyColumnNamesDict quyết định cột nào đi xuống bảng tạm, …CompareDict quyết định điều kiện “có thay đổi không”, …UpdateDict quyết định SET cột nào. PropertiesToInclude của TruePos thu hẹp cả ba cùng lúc, đó là lý do BulkUpdateAsync(list, opt => opt.PropertiesToInclude = [IsDraft]) chỉ ghi đè một cột.

5. SQL Server: SqlBulkCopy + MERGE

Đường nhanh: Insert không cần Id

Chuyển IList<T> thành DataTable (cột theo TableInfo, giá trị đã qua converter), mở SqlBulkCopy trên connection và transaction hiện tại của DbContext, WriteToServer thẳng vào bảng đích. Không có SQL nào được sinh. BatchSize, BulkCopyTimeout, NotifyAfter, EnableStreaming và SqlBulkCopyOptions đi thẳng vào object SqlBulkCopy.

Đường Merge: mọi thao tác còn lại

Câu MERGE thật mà SqlQueryBuilder.MergeTable sinh ra cho BulkInsertOrUpdateAsync(list, opt => opt.SetOutputIdentity = true) trên một bảng có identity Id và cột Code, Name, Status:

DECLARE @temp INT;
MERGE [dbo].[CrmSanPham] WITH (HOLDLOCK) AS T
USING (SELECT TOP 3 * FROM [dbo].[CrmSanPhamTemp8f2c1e0a] ORDER BY [Id]) AS S
ON T.[Id] = S.[Id]
WHEN NOT MATCHED BY TARGET THEN
    INSERT ([Code], [Name], [Status]) VALUES (S.[Code], S.[Name], S.[Status])
WHEN MATCHED AND EXISTS (SELECT S.[Code], S.[Name], S.[Status]
                        EXCEPT SELECT T.[Code], T.[Name], T.[Status]) THEN
    UPDATE SET T.[Code] = S.[Code], T.[Name] = S.[Name], T.[Status] = S.[Status]
OUTPUT INSERTED.[Id], INSERTED.[Code], INSERTED.[Name], INSERTED.[Status]
    INTO [dbo].[CrmSanPhamTemp8f2c1e0aOutput];
  • WITH (HOLDLOCK): giữ range lock suốt câu MERGE để hai request upsert cùng khoá không chèn trùng. TruePos tắt ở nhiều chỗ (WithHoldlock = false) để giảm deadlock khi biết chắc không có ghi đồng thời.
  • EXISTS (SELECT … EXCEPT SELECT …): chỉ UPDATE khi thực sự có cột khác; xử lý NULL đúng, khác với so sánh <>. Đây là lý do rowversion không bị nhảy nếu dữ liệu không đổi.
  • SELECT TOP N … ORDER BY trong USING: ép SQL Server duyệt source theo thứ tự khoá để OUTPUT ra đúng thứ tự, phục vụ ánh xạ Id ở mục 6.
  • DECLARE @temp: khi không có cột nào để update nhưng vẫn cần OUTPUT dòng MATCHED, thư viện thêm WHEN MATCHED THEN UPDATE SET @temp = 1 làm no-op.

6. Lấy lại Identity đúng thứ tự

Bảng OUTPUT trả về N dòng có Id thật, nhưng SQL Server không hứa thứ tự nào. Thư viện giải bằng thủ thuật PreserveInsertOrder trong TableInfo.CheckToSetIdentityForPreserveOrder:

  1. Gán Id âm tạm thời

    Trước khi BulkCopy, entity có Id == 0 được gán lần lượt -N, -N+1, …, -1 theo đúng thứ tự trong list. Entity đã có Id dương giữ nguyên.

  2. Bảng tạm giữ Id âm

    Cột Id trong bảng tạm không phải identity (nhờ LEFT JOIN … ON 1=0 khi tạo), nên nhận giá trị âm bình thường. MERGE với ORDER BY Id duyệt các dòng mới theo thứ tự -N → -1.

  3. Id âm không bao giờ khớp

    ON T.Id = S.Id với Id âm luôn NOT MATCHED, nên đi nhánh INSERT và server sinh identity mới tăng dần theo đúng thứ tự duyệt.

  4. Đọc OUTPUT, ghép theo vị trí

    SELECT … FROM Output ORDER BY Id: dòng thứ k của kết quả ứng với entity mới thứ k. Với upsert, entity có Id sẵn được sort trước theo Id, entity mới nối sau, rồi ghép 1-1.

  5. Reset khi không có OUTPUT

    Nếu chỉ Insert thường, Id âm được đặt lại về 0 sau khi ghi để entity trong bộ nhớ không mang giá trị rác.

Điểm yếu đã biết: nếu UpdateByProperties khớp nhiều dòng trong bảng cho một entity, ánh xạ 1-1 vỡ. Fork MIT thêm cơ chế thứ hai UseOriginalIndexToIdentityMappingColumn: thêm cột __OriginalIndex vào bảng tạm và OUTPUT, ghép theo chỉ số thay vì theo thứ tự. TSD.BulkExtensions sẽ dùng cách chỉ số làm mặc định vì đơn giản và không phụ thuộc thứ tự MERGE.

7. PostgreSQL: COPY BINARY + ON CONFLICT

PostgreSQL không có SqlBulkCopy và không có MERGE (trước bản 15). Adapter dùng hai công cụ khác nhưng cùng hình dạng luồng.

SQL Server

  • Stream: SqlBulkCopy.WriteToServer(DataTable)
  • Bảng tạm: SELECT TOP 0 … INTO trong schema đích
  • Upsert: MERGE … WHEN MATCHED / NOT MATCHED
  • Delete: MERGE … WHEN MATCHED THEN DELETE
  • Lấy Id: OUTPUT INSERTED.* INTO bảng output, đọc sau
  • Khoá tuỳ chọn: bất kỳ cột nào, không cần index

PostgreSQL

  • Stream: NpgsqlBinaryImporter = COPY … FROM STDIN (FORMAT BINARY), ghi từng cột với kiểu PG rõ ràng
  • Bảng tạm: CREATE TEMP TABLE … (LIKE đích INCLUDING DEFAULTS) hoặc bảng thường nếu UseTempDB=false
  • Upsert: INSERT … SELECT … FROM temp ON CONFLICT (keys) DO UPDATE SET c = EXCLUDED.c
  • Delete: DELETE FROM đích USING temp WHERE keys
  • Lấy Id: RETURNING * ngay trong câu INSERT, đọc bằng query EF
  • Khoá tuỳ chọn: bắt buộc có unique index. Không có thì thư viện tự CREATE UNIQUE INDEX rồi drop sau

Câu SQL PostgreSQL tương đương cho cùng thao tác upsert:

INSERT INTO "public"."CrmSanPham" ("Id", "Code", "Name", "Status")
    (SELECT "Id", "Code", "Name", "Status" FROM "public"."CrmSanPhamTemp8f2c1e0a")
ON CONFLICT ("Id")
DO UPDATE SET "Code" = EXCLUDED."Code", "Name" = EXCLUDED."Name", "Status" = EXCLUDED."Status"
RETURNING "Id", "Code", "Name", "Status";

Hai điểm khác biệt ngầm. Một: ON CONFLICT không có mệnh đề “chỉ update khi khác”, nên mọi dòng khớp đều bị UPDATE và trigger/rowversion đều chạy. Hai: BulkUpdate thuần (không insert) vẫn đi qua INSERT … ON CONFLICT DO UPDATE; entity không tồn tại sẽ bị insert mới thay vì bỏ qua. Đây là issue #171 còn mở ở fork MIT. TSD.BulkExtensions sẽ sinh UPDATE … FROM temp riêng cho Update.

Giá trị đi qua COPY BINARY phải khai báo đúng kiểu PostgreSQL (writer.Write(value, "numeric")). Adapter đọc GetColumnType() từ EF rồi chuẩn hoá: character varying(50) → character, numeric(18,2) → numeric. Enum có converter được ép về kiểu provider trước khi ghi.

8. IncludeGraph: insert cả cây đối tượng

Đơn hàng trong TruePos là một cây: DDonHang → DonHangChiTiet → DonHangChiTietLoHan, cộng thêm DonHangCoupon, DObjectLedger. Gọi BulkInsertAsync(new[]{ order }, opt => opt.IncludeGraph = true) thì thư viện tự ghi tất cả, theo đúng thứ tự khoá ngoại.

Chi tiết cài đặt trong DbContextBulkTransactionGraphUtil:

  • Ép ba config: PreserveInsertOrder = true, SetOutputIdentity = true, EnableShadowProperties = true. Không có ba thứ này thì không lấy được Id cha để điền vào con, đặc biệt khi FK là shadow property do EF tự tạo.
  • GraphUtil.GetFlatGraph duyệt entityType.GetNavigations() đệ quy, dùng Dictionary<object, GraphDependency> theo reference để chặn vòng lặp cha↔con.
  • Sắp xếp bằng MedallionTopologicalSort trên quan hệ “entity A phụ thuộc principal B”.
  • Lọc trùng khoá bằng GetUniqueEntities: cùng một sản phẩm xuất hiện trong nhiều dòng chi tiết chỉ Merge một lần.
  • Owned type nằm cùng bảng với owner thì bỏ qua lượt riêng, đã được làm phẳng ở TableInfo.
  • Nếu chưa có transaction, tự mở BeginTransaction và commit ở cuối; có lỗi giữa chừng thì dispose để rollback toàn bộ cây.

9. Transaction, connection và ABP

Thư viện không tự mở transaction cho thao tác đơn lẻ. Nó lấy context.Database.CurrentTransaction; nếu có thì mọi lệnh (SqlBulkCopy, tạo bảng tạm, MERGE, drop) chạy trong đó. Nếu không có, các lệnh chạy autocommit từng câu.

Trong ABP, mọi AppService method chạy trong UnitOfWork, và UoW đã BeginTransaction trên DbContext trước khi code nghiệp vụ chạy. Vì thế một chuỗi BulkDeleteAsync rồi BulkInsertAsync trong cùng method là atomic. Nếu UoW bị tắt ([UnitOfWork(IsDisabled = true)]) hoặc dùng IsTransactional = false, bulk sẽ chạy autocommit và bảng tạm được tạo/drop ngoài transaction.

Adapter mở connection bằng context.Database.OpenConnection() và đóng bằng CloseConnection() trong finally. EF Core đếm tham chiếu: nếu connection đã mở bởi transaction ABP thì CloseConnection không thực sự đóng. Thiết kế này phải giữ nguyên ở TSD.BulkExtensions, nếu không sẽ làm hỏng transaction của UoW.

10. Batch trên IQueryable

query.BatchDeleteAsync() và BatchUpdateAsync(x => new T { … }) không stream dữ liệu gì. BatchUtil lấy câu SELECT mà EF dịch từ LINQ (query.ToQueryString() + tham số), rồi cắt chuỗi: bỏ phần SELECT …, giữ FROM … WHERE …, ghép thành DELETE [alias] FROM … WHERE …. Với ORDER BY/TOP phải bọc CTE. Với UPDATE phải parse expression tree của lambda thành mệnh đề SET.

Cách này khoảng 1.000 dòng và mong manh vì phụ thuộc định dạng SQL EF sinh ra ở từng phiên bản. EF Core 7 đưa ExecuteDelete / ExecuteUpdate vào lõi, làm đúng việc này bằng query pipeline. Vì vậy TSD.BulkExtensions không viết lại BatchUtil: EF 8/10 gọi thẳng API lõi, EF 6 chuyển sang BatchDeleteAsync(predicate) của ABP EFPlus vốn đã có sẵn trong TruePos.

13. Điểm sẽ khác ở TSD.BulkExtensions

Giữ nguyên hình dạng luồng ở mục 2–9 vì đó là cách đúng để làm bulk trên hai engine này. Thay đổi nằm ở chi tiết cài đặt:

API công khai—Giữ nguyên 100% signature, đổi namespace TSD.BulkExtensions.

Tóm lại: thư viện này về bản chất là một bộ sinh SQL có hiểu model EF, cộng một lớp stream dữ liệu theo provider. Không có phép màu, nhưng có rất nhiều trường hợp biên đã được trả giá. Viết lại nghĩa là giữ luồng, giữ test, và bỏ những nhánh không ai dùng.
